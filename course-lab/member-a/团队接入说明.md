# B—E 接入公共工程

## 分工

| 成员 | 接入页面 | 数据职责 |
|---|---|---|
| B | 衣物列表、详情、录入、编辑、筛选 | 衣物、存放位置、私有图片上传与访问 |
| C | 搭配编辑、搭配列表、日历、计划 | 搭配与计划；调用 D 的确认实际穿着功能 |
| D | 实际穿着、洗护状态与历史、应用内提示 | 有效/作废记录、洗护变更、计划确认 |
| E | 统计概览、穿着次数、最近穿着日期 | 读取有效实际记录计算统计 |

## Android 接入

1. 拉取同一项目，在自己的分支开发。不要重新创建独立应用。
2. 为自己的页面创建独立 Activity 和 XML 布局，按 MVC 分离业务处理。
3. 在 Manifest 中注册内部 Activity，`exported=false`。
4. A 在 `HomeActivity` 中把相应 `module(...)` 点击入口改为跳转到你的真实 Activity。
5. 通过 `new SessionStore(context).token()` 获取当前登录凭证；统一通过 `EndpointStore.get(context)` 获取服务器地址。
6. 请求带 `Authorization: Bearer <token>`。不传数据库密码，不从 UI 自选 ownerId。
7. 收到 401 时清除登录凭证并返回登录页。切换账号后不能保留前一个账号的数据。
8. 不要把大图片 Base64 塞入账号 JSON；图片接口由 B 与后端统一设计。

所有网络请求都在后台执行；更新界面回到主线程。加载、空数据、错误、重试都要有明确状态。

## 后端接入

业务 Controller 调用 `AccountService.requireUser(authorization)` 验证登录，使用返回的 user.id() 作为当前 owner。
访问衣物、搭配、计划、实际记录和统计时，在查询和写入中校验归属。
同一后端共用一个数据库；不要按成员建立五个互不关联的数据库。
新建业务表的 owner_id 外键应引用 `users.user_id`，UUID 以字符串形式传输。

本次账号接口：

| 方法 | 路径 | 输入 | 返回 |
|---|---|---|---|
| POST | `/api/auth/register` | accountName, password, displayName | user |
| POST | `/api/auth/login` | accountName, password | token, user |
| GET | `/api/me` | Bearer 凭证 | user |
| PATCH | `/api/me` | displayName + Bearer 凭证 | user |
| POST | `/api/auth/logout` | Bearer 凭证 | 204 |

user 为 `{id, accountName, displayName}`，错误为 `{message}`。

## 共同规则

- 保存计划不增加穿着次数；有效实际记录才进入统计。
- 重复确认同一计划和实际日期返回已有记录，不能新增重复行；作废记录不自动恢复。
- 实际记录保存衣物成员快照，后续搭配编辑不改写历史成员。
- 洗护状态为 READY_TO_WEAR、TO_WASH、WASHING，独立于存放位置。
- 历史保留、闲置阈值和 30 天过期细则待全组确认，不擅自加入自动删除。
- 首版没有拍照、旅行清单、外部推送或管理员模块。

每次提交注明做了什么、依赖谁的接口、如何验证。各成员修复自己模块的问题，A 负责公共工程和合并协调。
